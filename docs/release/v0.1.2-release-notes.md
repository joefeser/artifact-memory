# Artifact Memory 0.1.2 release notes

Artifact Memory 0.1.2 is a backward-compatible release-candidate and adoption
clarity update over v0.1.1. It adds a reviewed public path for supplemental
keyless release-asset attestations, represents their pre-publication state
honestly, and sharpens the boundary between durable memory and WITS-owned
meaning and authority.

Release status is established only by a dedicated owner-signed annotated
`v0.1.2` tag and its verified release-manifest binding. This document is the
reviewed release body in the source tree; its presence alone does not claim
that signing, publication, or a keyless attestation has occurred.

## Repository adoption

- Public adoption prompts now guide another repository through a read-only fit
  audit, one provider-free synthetic proof, bounded context-pack consumption,
  and an evidence-backed adoption decision.
- Adoption remains pinned to an owner-signed release. Context packs and recalled
  prose are informational input, not instructions or execution authority.
- Context sensitivity, lifecycle, provenance, and limitations remain visible
  at the consumer boundary rather than being flattened into trusted memory.

## WITS ownership vocabulary

- Released v1/v2 WITS projections retain the frozen `owner-meaning` wire
  identifier. That compatibility name is not proof that Artifact Memory
  authenticated an owner decision.
- This release introduces no successor projection identifier.
  `admitted-owner-decision` remains reserved design vocabulary, while
  human-originated meaning describes provenance rather than a wire value.
- The authorized human originates and approves product meaning. WITS
  authenticates applicable authority, admits the human decision, and governs
  its recorded lifecycle, conflict handling, and routing without originating,
  owning, or independently approving that meaning. Artifact Memory records and
  context packs never create those powers.

## Release attestations

- A reviewed public GitHub Actions workflow can reproduce and verify an
  owner-published release asset set before requesting supplemental keyless
  Sigstore attestations.
- The workflow checks the exact tag, owner SSH signature, manifest trailer,
  source tree, deterministic assets, checksums, candidate receipts, published
  asset set, repository identity, and immutable workflow revision.
- Third-party actions are pinned to reviewed immutable commits. A failed gate
  emits no passing Artifact Memory receipt and requests no attestation.
- Keyless evidence proves workflow identity and subject digests. It does not
  replace owner signing or grant publication, execution, deployment, spending,
  credential, disclosure, declassification, or merge authority.

## Versioned pending-attestation contracts

- `release-manifest/v3` represents keyless attestation as required and
  `pending-post-publication` before a release exists.
- V3 preparation receipts state that attestation evidence is absent; v3
  signed-candidate verification receipts state that it was not evaluated.
- Candidate contracts reject premature `published` or `verified` states and
  reject embedded attestation URLs or bundles.
- Release identity selects the fail-closed contract: v0.1.0 and v0.1.1 retain
  their frozen v2 manifests, while v0.1.2 and later release candidates require
  v3. Historical schema, fixture, receipt, asset, and tag bytes are unchanged.

## Compatibility

All published v0.1.0 and v0.1.1 contracts remain readable under their original
semantics. New behavior is negotiated through v3 schema identifiers; no v1 or
v2 payload is reinterpreted. Unknown optional extensions remain preserved, and
unknown required extensions continue to fail closed.

Repository adoption documentation continues to pin consumers to the published
v0.1.1 release until v0.1.2 is separately owner-signed and published.

## Known limitations

- Merging this source does not create or push a tag, publish a release, invoke
  the attestation workflow, or prove an attestation exists.
- Post-publication attestation verification depends on GitHub and current
  Sigstore trust roots unless the bundle and an appropriate trusted-root
  snapshot are preserved for offline verification.
- Artifact Memory remains a local reference runtime rather than a hosted
  service, semantic retrieval system, checkpoint store, MCP server, or general
  agent execution runtime.
- Revocation and deletion provide only bounded endpoint and recipient
  evidence; they do not prove global erasure.

## Verification

Candidate preparation must produce a v3 pending release manifest and v3
preparation receipt from the exact reviewed source commit in an external empty
directory. The deterministic source archive, these exact notes, canonical
`SHA256SUMS`, schema inventory, public signing fingerprint, release identity,
and source-tree digest are cross-bound before any owner signing decision.
